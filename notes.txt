Summary
The issue was a Coordinate Reference System (CRS) mismatch:

Your graph was in WGS84 (EPSG:4326 - lat/lon coordinates)
Your raster was in ETRS89 LAEA Europe (EPSG:3035 - projected meters)
The solution was to:

Reproject the graph to EPSG:3035 to match the raster
Load the elevation data on the projected graph
Calculate edge grades on the projected graph
Reproject back to WGS84 for consistency
The 0.0% grade result is now correct because Sliema, Malta is genuinely a flat coastal area where all the street network nodes are at the same elevation level in this dataset

OSMNX
MultiDiGraphs are nonplanar directed graphs with possible self-loops and parallel edges. Thus, a one-way street will be represented with a single directed edge from node u to node v, but a bidirectional street will be represented with two reciprocal directed edges (with identical geometries): one from node u to node v and another from v to u, to represent both possible directions of flow.

Also if there are multiple lanes in same direction there will be a lanes attribute.

“if the path is NOT one-way, reverse direction of each edge and add this path going the opposite direction too” (https://github.com/gboeing/osmnx/blob/main/osmnx/graph.py)
Because OSMnx copies the way attributes into both directed edge additions, both directions can end up carrying lanes=1 as metadata. That does not mean the road has one lane in each direction; it means the original OSM way had lanes=1, and OSMnx attached that same way-level tag to both directed representations. Although if there is something like 4lanes, they should be split evenly between edges, allegdly.
If my understanding is correct, if lanes are None, but road is tagged as two way, then osmnx will create edges in both directions but without a lanes attribute.
